Fundamentos

Historia de la tecnología

De proyecto personal de un ex‑desarrollador de Lotus Notes a proyecto de la Apache Software Foundation.

02 / 18
2005
Damien Katz, ex‑ingeniero de Lotus Notes en IBM, comienza CouchDB en Erlang y lo autofinancia casi dos años antes de publicarlo.
2008
Ingresa como proyecto del Apache Incubator; la licencia pasa a Apache License 2.0.
2010
Se libera la versión 1.0 y CouchDB se gradúa como proyecto de primer nivel de Apache.
2012
Katz deja el proyecto para dedicarse a Couchbase Server — un fork comercial, hoy un producto distinto que no debe confundirse con CouchDB.
2013
Se fusiona el código de BigCouch (el clustering de Cloudant) al proyecto Apache, sentando la base del clustering nativo.
2016
CouchDB 2.0: clustering nativo (sharding), la interfaz Fauxton y el motor de consultas Mango sin necesidad de JavaScript.
2020
CouchDB 3.0: elimina el modo inseguro por defecto ("Admin Party") y exige crear un usuario administrador al instalar.
2026
Versión estable vigente: 3.5.2. Desarrollo activo con miles de commits y una comunidad de la ASF.

El nombre

"Couch" es un acrónimo de Cluster Of Unreliable Commodity Hardware: la idea fundacional de que la base de datos debe seguir funcionando aunque el hardware que la sostiene sea barato, disperso y falle.

Fundamentos

Arquitectura y fundamentos

Cuatro decisiones de diseño que explican todo lo demás: documentos JSON, MVCC, un archivo append‑only y una API que es HTTP puro.

03 / 18
  • Documento = unidad de datos. Cada registro es un objeto JSON con _id único y _rev (número de revisión). No hay tablas ni filas.
  • MVCC (control de concurrencia multiversión): cada escritura crea una nueva revisión en vez de sobrescribir. Las lecturas nunca bloquean a las escrituras, ni viceversa.
  • Erlang/OTP como runtime: el mismo motor de concurrencia masiva y tolerancia a fallos que usan las centrales telefónicas — de ahí la fama de estabilidad de CouchDB.
  • Todo es HTTP. No existe un driver binario propietario: GET, PUT, POST, DELETE sobre URLs son la única API. Se puede administrar una base entera con curl.
Fundamentos

Métodos para el diseño de esquema

CouchDB no impone esquema, pero diseñar bien un modelo documental sigue siendo un oficio con reglas propias.

04 / 18
  • Modelar por agregado de negocio, no por tabla normalizada: un documento agrupa todo lo que se lee junto (pensar "entidad completa", no "fila").
  • Embeber vs. referenciar: se embebe cuando el sub‑dato se lee siempre junto al padre y no crece sin límite (ej. dirección dentro de un cliente); se referencia por _id cuando el dato es compartido por muchos documentos o puede crecer indefinidamente (evita documentos gigantes).
  • Campo discriminador type: como no hay tablas, cada documento declara su "clase" ("type":"lectura_medidor") para poder filtrarlo en vistas y consultas.
  • Diseño orientado a las consultas ("query‑first"): las vistas son índices pre‑calculados, así que conviene decidir qué preguntas se van a hacer antes de escribir el modelo, no después.
  • _id con significado: usar prefijos tipo zona:fecha:secuencia permite recorrer rangos de _id ordenados de forma eficiente, sin índice extra.
  • Documentos pequeños y de responsabilidad única reducen la probabilidad de conflicto cuando hay escritura multi‑maestro, y facilitan el merge manual si igual ocurre.
  • _design documents agrupan vistas, filtros de replicación y reglas de validación (validate_doc_update): en la práctica, son "el esquema" de la base.
Práctica

Ejemplo ficticio: "OSE Móvil"

Una app hipotética de lectura de medidores para inspectores que trabajan en zonas rurales sin cobertura estable.

05 / 18

Cada tablet corre PouchDB (el hermano JavaScript de CouchDB) de forma local. El inspector carga lecturas todo el día sin señal; al volver a una zona con cobertura, la app sincroniza automáticamente contra el servidor central.

documento · lecturas/00234-2026-09-13
{
  "_id": "lectura:2026-09-13:00234",
  "_rev": "1-8a3f21c9",
  "type": "lectura_medidor",
  "medidor_id": "OSE-4471",
  "zona": "Canelones-Este",
  "inspector": "jperez",
  "fecha": "2026-09-13T14:32:00-03:00",
  "valor_m3": 18452.7,
  "sincronizado": false,
  "geo": { "lat": -34.708, "lon": -55.982 }
}
design document · _design/lecturas
{
  "_id": "_design/lecturas",
  "views": {
    "por_zona": {
      "map": "function(doc){ if(doc.type==='lectura_medidor'){ emit(doc.zona, doc.valor_m3); } }"
    },
    "pendientes_sync": {
      "map": "function(doc){ if(doc.type==='lectura_medidor' && !doc.sincronizado){ emit(doc._id, null); } }"
    }
  }

Práctica

Lenguaje de consulta

Tres formas de preguntar: la API HTTP cruda, vistas MapReduce, y Mango — el buscador declarativo sin JavaScript.

06 / 18
MétodoEndpointUso
GET/db/{id}Leer un documento por su clave
PUT/db/{id}Crear o actualizar (requiere _rev vigente)
POST/db/_bulk_docsInsertar o actualizar en lote
DELETE/db/{id}?rev=..Borrar (deja una "tumba")
GET/db/_design/x/_view/yConsultar una vista MapReduce
POST/db/_findConsulta Mango (tipo Mongo)

Vistas MapReduce

Una función map recorre cada documento y emite pares clave/valor. El resultado es un índice B‑tree incremental, que opcionalmente se agrega con reduce (_sum, _count, _stats).

Con clave compuesta ([zona, año, mes]) una sola vista responde varios niveles de agregación: el parámetro group_level elige cuánto detalle querés. Eso es drill‑down sin escribir una vista por nivel.

Mango (desde 2.0)

Consultas declarativas por JSON, estilo MongoDB, sin escribir funciones. Requiere un índice (_index) sobre los campos que se filtran, o recorre la base entera. _explain dice cuál eligió el planificador.

Su límite: Mango no agrega. No tiene reduce ni group_by. Para "cuántos m³ por zona" hay que usar una vista igual.

POST /inspecciones/_find
{
  "selector": {
    "type": "lectura_medidor",
    "zona": "Canelones-Este",
    "valor_m3": { "$gt": 15000 }
  },
  "fields": ["_id","medidor_id","valor_m3"],
  "sort": [{"valor_m3":"desc"}],
  "limit": 20
}
Distribución

Replicación y sincronización

La característica que distingue a CouchDB del resto: replicación multi‑maestro nativa, pensada para el modo offline.

07 / 18
  • Protocolo de replicación Couch: puede ser puntual o continuo, push o pull, filtrado por función, y corre entre cualquier par de nodos CouchDB — o CouchDB y PouchDB — sin jerarquía fija.
  • Offline‑first por diseño: el dispositivo trabaja siempre contra su copia local; la sincronización con el resto del mundo es un proceso aparte que se retoma solo cuando hay red.
  • Conflictos, no bloqueos: si dos réplicas editan el mismo documento sin verse, CouchDB no pierde datos: guarda todas las revisiones en conflicto (_conflicts), marca una "ganadora" determinística para no romper lecturas simples, y deja la fusión real en manos de la aplicación.
_replicate continuous: true filtered replication PouchDB.sync()
POST /_replicate
{
  "source": "inspecciones",
  "target": "http://central.ose.local:5984/inspecciones",
  "continuous": true
}

PouchDB · el otro extremo del protocolo

El protocolo no lo habla solo CouchDB. PouchDB es una implementación en JavaScript que corre dentro del navegador o de la app móvil, guardando en IndexedDB, y sincroniza contra un CouchDB con una línea: db.sync('http://servidor/base'). Eso es lo que hace realista el "OSE Móvil" de la slide 05: la tablet no necesita un servidor instalado, alcanza con la app.

En la demo que viene, la tablet B es exactamente esto: una página que abre su base con new PouchDB('inspecciones') y sincroniza con live: true. La tablet A, en cambio, es un nodo CouchDB completo. El central no nota la diferencia.

Distribución

Almacenamiento, distribución y escalamiento

De un único archivo append‑only a un clúster con particiones (shards) y réplicas internas.

08 / 18
  • Single node: una base = un archivo .couch. Simple, suficiente para equipos chicos o instalaciones edge.
  • Clustering nativo (2.0+): cada base se parte horizontalmente en shards (parámetro q) y cada shard se replica en varios nodos (parámetro n). El enrutado de cada request al shard correcto lo resuelve internamente el clúster.
  • Escalamiento horizontal: agregar nodos rebalancea los shards; no requiere reescribir la aplicación porque la API HTTP no cambia entre modo single‑node y clúster.

Configuración de clúster (local.ini)

[cluster]
n = 3
q = 8

Operación

Configuración y administración

Todo se puede configurar por archivo o en caliente por HTTP; toda la administración visual vive en Fauxton.

09 / 18
  • default.ini trae los valores de fábrica (no se edita); local.ini guarda los overrides del sitio; también admite un directorio .d/ de configuración modular.
  • API de configuración en caliente: PUT /_node/{nodo}/_config/{sección}/{clave} cambia casi cualquier parámetro sin reiniciar el proceso.
  • Fauxton: panel web de administración (sucesor de Futon) para bases, documentos, vistas, usuarios, réplicas y logs.
  • Usuarios y roles: se gestionan en la base especial _users; cada base define su propio documento _security con roles admin/members.
  • Imagen oficial de Docker y Helm chart oficial para Kubernetes simplifican el despliegue.
PUT /inspecciones/_security
{
  "admins": { "names": [], "roles": ["_admin"] },
  "members": {
    "names": [],
    "roles": ["inspectores", "supervisores"]
  }
}
Operación

Seguridad en tráfico y en reposo

Autenticación, TLS y un límite importante a tener claro: el cifrado en disco no lo resuelve CouchDB.

10 / 18

En tránsito

  • TLS/HTTPS nativo (sección [ssl]) o terminado en un proxy inverso (Nginx, HAProxy).
  • CORS configurable y cabeceras como X-Frame-Options.
  • Autenticación: Basic Auth, Cookie Auth, Proxy Auth y JWT (desde 3.x) para integrarse con un IdP externo.

En reposo

  • Desde 3.0 es obligatorio crear un admin al instalar: se eliminó el modo "Admin Party" (acceso total sin login).
  • Autorización granular con el documento _security por base y funciones validate_doc_update a nivel documento.
  • CouchDB no cifra el archivo .couch en disco: el cifrado en reposo se resuelve con cifrado de disco/filesystem (LUKS, EBS, etc.) — o, en la nube, lo aporta el proveedor (Cloudant usa IBM Key Protect).
Operación

Backups

Tres estrategias, de la más simple a la más operativa, y ninguna requiere apagar el servicio.

11 / 18
  • Copia de archivos: como el motor de almacenamiento es append‑only, copiar la carpeta de datos en caliente (con fsync) es seguro.
  • Backup lógico: la herramienta oficial couchbackup exporta cada documento a un archivo JSON‑lines; couchrestore lo reimporta.
  • Replicación como backup: mantener una réplica continua en otro nodo u otra región cumple la función de un backup "caliente" siempre al día.
  • Buenas prácticas: versionar los backups por fecha y probar la restauración periódicamente — un backup que nunca se restauró no está verificado.
terminal
couchbackup --db inspecciones --url http://admin:pass@localhost:5984 \
  > inspecciones_2026-09-13.jsonl

couchrestore --db inspecciones_restaurada --url http://admin:pass@localhost:5984 \
  < inspecciones_2026-09-13.jsonl

Performance

MVCC sin locks favorece la escritura concurrente; las vistas y la compactación son las palancas que hay que operar.

12 / 18
  • Lectura por _id: resolución directa por B‑tree, muy rápida y estable.
  • Vistas: la primera consulta puede ser costosa si el índice no está construido; conviene "calentar" las vistas después de cada despliegue. Después son incrementales.
  • Compactación: reduce el tamaño en disco y mejora el I/O; no bloquea, pero conviene programarla en ventanas de bajo uso.
  • _bulk_docs / _bulk_get: agrupar operaciones reduce drásticamente los round‑trips HTTP.
  • Mango sin índice cae a recorrido completo de la base — crear el _index adecuado es tan importante como en cualquier motor SQL.
  • Frente a un RDBMS: mejor throughput de escritura para documentos independientes (no hay locks de fila/tabla); peor para joins o agregaciones complejas entre múltiples documentos, que CouchDB no resuelve de forma nativa.
Adopción

Uso en cloud

IBM Cloudant es el camino gestionado oficial; también corre como cualquier otra carga contenerizada.

13 / 18

IBM Cloudant

DBaaS totalmente gestionado, construido sobre Apache CouchDB — de hecho, su motor de clustering (BigCouch) terminó fusionado de vuelta al propio proyecto Apache en 2013.

Modelo
Serverless, escala cómputo y almacenamiento por separado
Disponibilidad
6 regiones, múltiples zonas, SLA 99,99%
Seguridad
Cifrado con IBM Key Protect + integración IAM
  • Autogestionado en cloud: imagen Docker oficial y Helm chart corren igual en AWS, GCP, Azure o cualquier Kubernetes.
  • Encaja bien en arquitecturas edge/móviles: el propio protocolo de replicación reemplaza a buena parte de un backend de sincronización a medida.
  • Alternativas de terceros existen en distintos marketplaces, pero Cloudant es la única oferta gestionada respaldada directamente por un proveedor mayor.

Qué vamos a ver funcionando

El mismo caso "OSE Móvil" de la slide 05, pero ejecutándose: tres nodos CouchDB reales en Docker, dos tablets de campo y el panel del central.

15 / 18
  1. 01
    Escritura sin conexión. Una lectura nueva se guarda en la tablet aunque el central esté inalcanzable.
  2. 02
    Dos clientes distintos. Una tablet es un nodo CouchDB y la otra es PouchDB en el navegador. El central replica con las dos igual.
  3. 03
    Replicación filtrada. Cada inspector solo baja sus propias lecturas; el consolidado de todos vive en el central.
  4. 04
    Vista MapReduce. Los m³ por zona salen de la vista por_zona con reduce: _stats.
  5. 05
    Consulta Mango. Filtro por zona y mínimo de m³, usando el índice creado en el setup.
  6. 06
    Conflicto multi‑maestro. Dos inspectores midieron el mismo medidor sin verse: ninguna versión se pierde.
  7. 07
    Se cae un master. Bajamos un central en vivo: el otro sigue aceptando escrituras y, cuando vuelve, se pone al día solo.
  8. 08
    Resolución. La aplicación elige cuál vale y borra la revisión perdedora — ahí se cierra el conflicto.

Adopción

Ejemplos de uso: cuándo sí, cuándo no

La pregunta no es "¿es buena?" sino "¿el problema es el que CouchDB resuelve mejor?"

16 / 18

Encaja bien

  • Apps móviles/offline‑first con sincronización multi‑dispositivo
  • Catálogos, perfiles y sistemas de gestión de contenidos
  • Captura de datos IoT que se genera desconectada
  • Sistemas donde importa auditar el historial de revisiones

Conviene evitar

  • Reportes analíticos con joins complejos entre muchas entidades
  • Transacciones estrictas multi‑documento (ACID es solo a nivel de un documento)
  • Agregaciones ad‑hoc pesadas — mejor un data warehouse aparte
Cierre

Opinión personal

Qué me convenció y qué no, después de investigar la tecnología y de armar la demo con tres nodos reales.

17 / 18

Lo que más me gustó de CouchDB es que hace una cosa sola y la hace bien. La replicación multi‑maestro y el trabajo offline no son algo que le agregaron después, es para lo que nació el proyecto en 2005 y se nota. Armando la demo me llamó la atención lo poco que hay que pelearse con la herramienta: no instalé ningún driver, hice todo con curl y con fetch desde una página HTML común.

Lo que no me cerró tanto: la comunidad es bastante más chica que la de MongoDB, y fuera de Cloudant casi no hay opciones de nube gestionada, así que si mañana querés delegar la infraestructura tenés poco de dónde agarrarte. Las vistas MapReduce me costaron más de lo que esperaba, porque hay que pensar la consulta antes de escribir el modelo y eso se siente raro viniendo de SQL. Y todo el tema de shards y quorum es una curva que un proyecto chico capaz nunca necesita subir.

¿La usaría? Para un CRM o una app de ventas común, no, me iría a algo más convencional. Pero para el caso de la demo, gente en la calle cargando datos sin señal y sincronizando cuando puede, no encontré nada que lo resuelva tan directo. Ese es el nicho donde CouchDB no tiene mucha competencia.
