01 · El problema

Dos exigencias opuestas en el mismo sistema

Lecturas

Catálogo y perfiles

  • Muchas consultas de usuarios y eventos
  • Rápidas y escalables
  • Prioridad: disponibilidad y tolerancia a particiones
  • Se acepta consistencia eventual
Escrituras

Reservas y pagos

  • Muchos compradores a la vez sobre el mismo stock
  • Prioridad: consistencia fuerte
  • Nunca vender de más ni cobrar dos veces
  • Transacción que cruza servicios y bases
Requisitos

Del enunciado

  • Al menos 2 bases NoSQL
  • SAGA con orquestación
  • Chain of Responsibility
  • Docker Compose
  • Opcionales: JMeter, Event Sourcing, CQRS, anonimización

06 · Consistencia por operación

Cada operación elige su lado del teorema CAP

OperaciónPriorizaCómoGarantía
GET /api/usuarios/{id}
GET /api/eventos/{id}		APCaché Redis stale-if-error delante de MongoDBResponde aunque MongoDB caiga; el dato puede estar hasta 30 s viejo (más si MongoDB está caído)
POST /api/reservarCPLua atómico + idempotencia + SAGA con compensación + w=majorityNunca vende de más ni cobra dos veces; si no puede garantizarlo, responde error
Lectura dentro de la SAGACPCache-Control: no-cacheNunca usa un dato vencido para decidir una compra

Honesto: cada base corre en un solo nodo. La read preference y w=majority están configurados, pero sin replica set no se ejercitan; la disponibilidad de lecturas se demuestra con la caché.

08 · Chain of Responsibility

El patrón en el código

# chain/handler.py
class BaseHandler(Handler):
    async def handle(self, ctx):
        if ctx.error:          # la cadena ya se cortó
            return ctx
        await self._process(ctx) # el paso propio
        if ctx.error:
            return ctx
        return await self._execute_next(ctx)

# chain/validators.py · ChainBuilder.build()
datos.set_next(usuario)
usuario.set_next(evento)
evento.set_next(pago)
pago.set_next(confirmacion)
confirmacion.set_next(auditor)

Una responsabilidad por handler

Validar, cobrar, confirmar y auditar están separados y se testean por separado.

Corte temprano

Un error en los pasos 1-3 evita tocar Redis o MongoDB: no hay nada que compensar.

Compensación localizada

Solo los handlers 4 y 5 modifican estado, y solo ellos saben deshacerlo.

10 · Atomicidad

No hay doble venta: el stock lo decide un script Lua

-- pagar_y_decrementar (Redis ejecuta un script por vez)
if redis.call('EXISTS', pago_key) == 1 then
  return {1, ya_pagado}        -- idempotente
end
redis.call('SETNX', inventario_key, seed)
local disponible = tonumber(redis.call('GET', inventario_key))
if disponible < cantidad then
  return {-2, disponible}      -- sin stock, nada cambia
end
redis.call('DECRBY', inventario_key, cantidad)
redis.call('HSET', pago_key, ...)  -- registra el pago
redis.call('EXPIRE', pago_key, ttl)
return {1, disponible - cantidad}

11 · Idempotencia y resiliencia

Reintentar siempre es seguro

sequenceDiagram
  participant C as Cliente
  participant R as Reservas
  participant E as Eventos
  Note over E: caído
  C->>R: POST reserva_id = A
  R-xE: 3 reintentos · 0,5 / 1 / 2 s
  R-->>C: 503 (nada cobrado)
  Note over E: vuelve
  C->>R: POST reserva_id = A
  R->>E: OK
  R-->>C: 201 confirmada
  C->>R: POST reserva_id = A
  R-->>C: 200 ya existía

Idempotencia por reserva_id

Ya confirmada en MongoDB → 200. El Lua no cobra dos veces. El historial usa $ne.

Reintentos con backoff

3 reintentos ante timeout o 5xx; un 404 no se reintenta.

Circuit breaker

5 fallos seguidos → abierto 30 s, rechaza al instante; después prueba con una petición (half-open).

Event sourcing de auditoría: cada paso, incluidos fallos y compensaciones, queda como evento inmutable. El estado operativo vive en MongoDB (sin replay). Las ventas se cuentan por RESERVA_CONFIRMADA: un cobro compensado no las infla.

Escribir el log no bloquea la compra: si PostgreSQL cae, la reserva sigue16

¿Por qué no un hash?

Un DNI o un nombre hasheado sin clave se revierte por diccionario en segundos.

Anonimizar vs seudonimizar

Sin clave configurada es efímera (anonimización); con clave fija, seudónimos estables.

JSON y CSV

El CSV neutraliza la inyección de fórmulas. Los datos personales viven en un único documento.

14 · Límites

Lo que no está resuelto (y lo decimos)

Rendimiento

La SAGA completa satura en ≈ 50 req/s: no se cumple p99 < 1 s a 100 req/s. Descartados: CPU de Python y commit sincrónico de PostgreSQL. Sospechas: journal de MongoDB, proxy de Docker en WSL2.

Un nodo por base

Sin replica set ni réplica de Redis. Antes de agregar réplicas hay que ajustar la read preference (maxStalenessSeconds ≥ 90).

Event sourcing parcial

El log es de auditoría; el estado no se reconstruye desde los eventos.

Deuda técnica

Una segunda capa de compensación en el orquestador es redundante y registra un evento de más cuando falla el paso 5.

Privacidad

Sin endpoint de baja, sin cifrado de campos, sin k-anonimato.
